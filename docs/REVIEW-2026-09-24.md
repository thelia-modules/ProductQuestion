# Review : module ProductQuestion (HEAD `2c1c4c9`, module complet, niveau approfondi)

Review de clôture de la phase 6, menée le 24 septembre 2026 sur les 45 fichiers applicatifs du
module (tests et fixtures parcourus). Trois angles croisés : correctness et règles métier,
architecture, sécurité. Les findings reproductibles ont été rejoués contre la boutique de
développement ; ceux établis sur pièces seulement le disent.

## Résumé

Module sain : contrôleur mince, règles métier centralisées dans trois services, deux portes
(LiveComponent, API) qui repassent par le même `ProductQuestionAsker`, CSRF et droits BO
corrects, payloads construits champ par champ, sanitizer robuste, gate verte (php-cs-fixer 0,
PHPStan level 6 : 0, 110 tests). Un bloquant réel de perte de données sur le cycle de vie du
module, et une série d'importants sur la robustesse de l'API publique et la symétrie des deux
portes.

- Fichiers reviewés : 45
- ❌ Bloquants : 1 | ⚠️ Importants : 8 | 💡 Suggestions : 14 | 🟣 Pré-existants : 2

## ❌ Bloquant (corriger avant merge)

### [ProductQuestion.php:76-89] Supprimer le module « en gardant les données » puis le réinstaller rejoue `DROP TABLE`

**Problème** : le garde-fou contre le rejeu de `TheliaMain.sql` est le flag `is_initialized`
dans `module_config`. Or `module_config` porte `fk_module_config_module_id … onDelete="CASCADE"`
(`local/config/schema.xml:2406`) : la suppression du module (`core/lib/Thelia/Action/Module.php`,
`destroy()` puis `$module->delete()`) efface le flag quel que soit le choix « supprimer les
données ». `destroy()` n'est pas surchargé (no-op, `BaseModule.php:552`), la table reste ; la
réinstallation ne trouve plus le flag et exécute `Config/TheliaMain.sql:10`
(`DROP TABLE IF EXISTS product_question`). Toutes les questions sont perdues, sans message.
Vérifié sur pièces (trois fichiers cités), non rejoué en base.

**Suggestion** : garder sur l'existence de la table, et honorer `$deleteModuleData` :

```php
public function postActivation(?ConnectionInterface $con = null): void
{
    $con ??= Propel::getConnection();

    if (!self::tableExists($con, 'product_question')) {
        (new Database($con))->insertSql(null, [__DIR__.DS.'Config'.DS.'TheliaMain.sql']);
    }

    (new ProductQuestionMessageInstaller())->install();
}

public function destroy(?ConnectionInterface $con = null, $deleteModuleData = false): void
{
    if (!$deleteModuleData) {
        return;
    }

    $con ??= Propel::getConnection();
    $con->exec('DROP TABLE IF EXISTS `product_question`');
    MessageQuery::create()->filterByName([self::MESSAGE_ADMIN_NOTIFICATION, self::MESSAGE_CUSTOMER_ANSWERED], Criteria::IN)->delete($con);
}

private static function tableExists(ConnectionInterface $con, string $table): bool
{
    $statement = $con->prepare('SHOW TABLES LIKE :table');
    $statement->execute(['table' => $table]);

    return false !== $statement->fetchColumn();
}
```

Le flag `is_initialized` peut alors disparaître. Preuve attendue : activer, poser une question,
supprimer le module en gardant les données, réinstaller, la question est toujours là.

## ⚠️ Important (fortement recommandé)

### [Service/ProductQuestionAsker.php:47-48] + [Api/State/ProductQuestionPostProcessor.php:68-84] Produit jamais vérifié : 500 sur commande

**Problème** : le POST accepte tout `productId > 0` ; rien ne vérifie l'existence ni la
visibilité du produit. `save()` heurte la FK, la `PropelException` n'est pas capturée (seule
`InvalidProductQuestionException` l'est). **Reproduit** : `productId: 999999` → HTTP 500, la
requête `INSERT` complète dans `detail` (en dev). Un jeton de rate-limit est consommé au passage.
Permet aussi de faire envoyer un mail à la boutique pour un produit brouillon.

**Suggestion** : dans l'asker, derrière un port testable :

```php
// Repository/ProductExistenceInterface.php
interface ProductExistenceInterface { public function isAskable(int $productId): bool; }

// Repository/ProductRepository.php
public function isAskable(int $productId): bool
{
    return ProductQuery::create()->filterById($productId)->filterByVisible(1)->exists();
}

// ProductQuestionAsker::ask(), après le test $productId <= 0
if (!$this->products->isAskable($productId)) {
    throw InvalidProductQuestionException::unknownProduct();
}
```

Le processor traduit déjà cette exception en 422 ; le composant en message générique.

### [Api/State/ProductQuestionProvider.php:71-89] Filtres publics lus sans contrôle de type

**Problème** : `$context['filters']` vient de `parse_str` : `?locale[]=x` livre un tableau.
**Reproduit** : `GET /api/front/product_questions?productId=1&locale[]=x` → HTTP 500 « Array to
string conversion » (trace exposée en dev) ; `?productId[]=foo` → 200 avec un produit fantôme
(`(int) ['foo']` vaut 1). Endpoint anonyme, coût nul pour l'appelant.

**Suggestion** :

```php
private static function scalar(array $filters, string $key): ?string
{
    $value = $filters[$key] ?? null;

    if (null !== $value && !\is_scalar($value)) {
        throw new BadRequestHttpException(\sprintf('The "%s" query parameter must be a single value.', $key));
    }

    return null === $value ? null : (string) $value;
}
// $productId = (int) (self::scalar($filters, 'productId') ?? 0); idem locale, page, itemsPerPage
```

Ajouter les deux cas au test du provider.

### [Twig/ProductQuestionBlock.php:121-129] Le LiveComponent dépense le budget avant la validation, l'API après

**Problème** : `ask()` consomme `askLimiter->allows()` puis `submitForm()`. Côté API,
`validationContext` fait tourner le validateur avant le processor : un texte trop court y coûte
0 jeton (prouvé), alors que trois fautes de frappe dans le composant épuisent le budget produit
d'une heure. Le PLAN affirme « The API and the component spend the same budgets » : le code le
contredit.

**Suggestion** :

```php
// Valider la forme d'abord : un re-rendu avec erreurs ne coûte rien ; le budget ensuite.
$this->submitForm();

if (!$this->askLimiter->allows($customerId, $this->productId)) {
    $this->error = $this->trans('Too many questions have been sent. Please try again later.');
    return;
}
```

Et l'écrire dans le PLAN si l'ordre inverse est finalement voulu.

### [Api/State/ProductQuestionProvider.php:93-105] + [Repository/ProductQuestionRepository.php:38-50] Pagination en PHP après lecture complète

**Problème** : `findAnsweredForProduct()` n'a ni `offset` ni `limit` ; la page est découpée par
`array_slice`. Coût proportionnel au total de réponses du produit, sur un endpoint anonyme, alors
que le README annonce « Paginated ».

**Suggestion** : `findAnsweredForProductPage(int $productId, string $locale, int $offset, int $limit): array{items: list<ProductQuestion>, total: int}`
dans le contrat, avec `->offset()->limit()` et `(clone $query)->count()`, comme
`searchForModeration` le fait déjà (`:110-124`). Le composant garde la lecture complète.

### [Service/Front/ProductQuestionAskLimiter.php:42-52] Budget clé sur le compte seul, inscription libre, un mail par question

**Problème** : deux fenêtres, toutes deux clés `customerId`. L'inscription front est ouverte et
chaque question envoie un mail synchrone à `store_notification_emails` : N comptes × 10/h =
N×10 mails et lignes de modération par heure, sans budget par adresse ni global.

**Suggestion** : troisième fenêtre par IP déclarée dans `configureContainer()`
(`product_question_ask_per_ip`, 20/h) et consommée dans le limiter via
`RequestStack::getCurrentRequest()?->getClientIp()`, comme `CommentPostLimiter` ; option : un
budget global à clé fixe (200/h) qui protège la boîte mail quoi qu'il arrive.

### [EventListener/ProductQuestionNotifier.php:81] + [EventListener/ProductQuestionCustomerNotifier.php:85] Message d'exception brut dans le log

**Problème** : `sprintf(... $exception->getMessage())`. Un `TransportException` SMTP reprend
souvent le dialogue serveur, destinataire compris (« 550 … <client@…> ») ;
`RfcComplianceException` embarque l'adresse. Pour le notifier client, c'est l'adresse d'un client
en clair dans le log d'erreur. Non vérifié à l'exécution (dépend du transport). L'interpolation
empêche aussi tout filtrage structuré.

**Suggestion** :

```php
$this->logger->error('ProductQuestion: the customer could not be told about the answer to question {id}.', [
    'id' => $questionId,
    'exception' => $exception, // Monolog le porte en contexte, filtrable par un processor
]);
```

### [Service/BackOffice/ProductQuestionListPresenter.php:98-109] + [EventListener/ProductQuestionNotifier.php:85-96] La règle « nom affiché d'un client » existe deux fois

**Problème** : deux `customerName()` identiques (prénom + nom, sinon e-mail). Seule duplication
de règle métier du module ; un changement (masquer l'e-mail dans le mail boutique) sera fait une
fois sur deux.

**Suggestion** : `Service/CustomerDisplayName::of(?object $customer): ?string`, fonction pure,
appelée aux deux endroits ; testable sans kernel (le double type déjà `getCustomer(): ?object`).

### [Controller/Back/ProductQuestionController.php:48-56, 92-120] Six dépendances et le view-model d'édition construit dans le contrôleur

**Problème** : `renderQuestion()` assemble statut, deux URLs admin du core codées en PHP, titre
produit, jeton ; `ProductTitleSourceInterface` et `ProductQuestionStatusCatalog` ne servent qu'à
cet écran. La liste a son présenteur, l'édition non. `$question` porte un PHPDoc au lieu d'un
type natif (`:89-92`).

**Suggestion** : `Service/BackOffice/ProductQuestionEditPresenter::present(ProductQuestion $question, string $uiLocale): array`
(statut, URLs via `ShopContextInterface` étendu de `customerAdminUrl()`/`productAdminUrl()`,
titre) ; le contrôleur redescend à quatre dépendances et n'ajoute que `form` et `csrfToken`.

## 💡 Suggestions

### [Controller/Back/ProductQuestionController.php:210] Jeton CSRF accepté en query string

**Problème** : repli `$request->query->get('_token')`. Routes `POST` seulement, donc pas
exploitable aujourd'hui, mais un jeton de session dans une URL fuit (Referer, historique, logs)
le jour où un lien tokenisé est construit. Le module n'en construit aucun.

**Suggestion** : `$token = (string) $request->request->get('_token', '');`

### [Controller/Back/ProductQuestionController.php:212-220] Refus CSRF silencieux

**Problème** : `checkToken` lève aussi pour un jeton différent ; le `catch` avale les deux cas
et redirige sans trace. Une tentative de forge sur le BO ne laisse rien.

**Suggestion** : `$this->adminLogAppend(ProductQuestionModule::getModuleCode(), 'csrf', 'Refused a moderation action: '.$exception->getMessage());`
dans le `catch`.

### [Service/Front/ProductQuestionTextSanitizer.php:48-60] Plafond de quatre passes

**Problème** : chaque passe retire un niveau d'imbrication ; cinq niveaux laissent un tag
stocké. Sans conséquence (toute sortie est échappée), mais l'invariant annoncé par la classe
n'est pas garanti. Pas de risque ReDoS (`[^<>]*` borné).

**Suggestion** : plafond à 16, et si `preg_match('#<[a-zA-Z]#', $clean)` subsiste, `strip_tags`
en dernier recours ou `InvalidProductQuestionException`.

### [Api/Resource/ProductQuestion.php:89-90] `locale` = toute chaîne de dix caractères

**Problème** : `Length(max: 10)` sans format. Une question sous `zz_ZZ` n'apparaît nulle part
mais alimente `findUsedLocales` et le `<select>` du BO (échappé).

**Suggestion** : `#[Regex('/^[a-z]{2}_[A-Z]{2}$/', groups: [self::GROUP_FRONT_WRITE])]`, ou
contrôle contre `LangQuery` dans l'asker.

### [Install/ProductQuestionMessageInstaller.php:95] Sujet compilé sous autoescape html (non vérifié)

**Problème** : le sujet `… "{{ question.productTitle }}"` est rendu par `renderString()` sans
nom d'extension → stratégie `html` : un produit nommé `L'Étoile` sortirait `&#039;` dans
l'en-tête `Subject`. Donnée admin, cosmétique.

**Suggestion** : vérifier en Mailpit avec un tel produit ; si confirmé,
`'{{ question.productTitle|raw }}'` est acceptable ici (le sujet n'est pas du HTML).

### [Twig/ProductQuestionBlock.php:111-141] + [Api/State/ProductQuestionPostProcessor.php:62-85] La séquence « client → budget → asker » est écrite deux fois

**Problème** : refuser un anonyme, dépenser le limiteur, traduire l'exception : dupliqué entre
les deux portes ; un troisième canal la recopierait.

**Suggestion** : un `AskQuestionHandler::handle(int $productId, ?int $customerId, string $locale, ?string $content)`
qui porte la séquence et lève `TooManyQuestionsException` ; chaque porte ne garde que la
traduction HTTP / message.

### [Repository/ProductQuestionStorageInterface.php:17,68] Le contrat de stockage dépend d'un objet qui lit `Request`

**Problème** : `Repository\` importe `Service\BackOffice\ProductQuestionListFilters`, qui importe
`HttpFoundation\Request`. Le port de persistance connaît la couche HTTP, et les deux couches se
référencent mutuellement.

**Suggestion** : `Repository/ProductQuestionSearchCriteria` pur (status, productId, customerId,
locale, page, limit, order) construit par `ProductQuestionListFilters`.

### [ProductQuestion.php:128-144] Exclusions incomplètes et commentaire d'alias inexact

**Problème** : `load()` enregistre `Install/*`, `Event/*`, `Exception/*` comme services privés
jamais référencés (retirés à la compilation : bruyant, pas nuisible). Symfony aliase seul une
interface à implémentation unique : quatre des cinq alias sont redondants, seul
`CurrentCustomerInterface` (deux implémentations) en a besoin ; le commentaire dit l'inverse. Ne
pas exclure `Form/` (`FormInterface` → tag `thelia.form`).

**Suggestion** : ajouter `Event/*`, `Exception/*`, `Install/*` aux exclusions ; corriger le
commentaire ou ne garder que l'alias nécessaire.

### [Install/ProductQuestionMessageInstaller.php:66-73] `addResource()` sur un fichier absent

**Problème** : pour une langue démo sans fichier, `PhpFileLoader` lève
`NotFoundResourceException`, avalée par le translator grâce au repli, mais le reste du catalogue
de cette locale n'est pas chargé dans le processus courant.

**Suggestion** : `if (is_file($file)) { $translator->addResource(...); }`.

### [EventListener/ProductQuestionNotifier.php:38] Deux abstractions pour deux mails

**Problème** : le notifier client passe par `CustomerMailerInterface`, celui de la boutique par
`MailerFactory` concret (mocké en concret dans son test).

**Suggestion** : élargir le port en `ModuleMailerInterface { sendToCustomer(); sendToShopManagers(); }`,
un seul double `SpyMailer`.

### [Repository/ProductQuestionStorageInterface.php:48] `findByCustomer()` sans appelant

**Problème** : défini, implémenté, doublé, jamais consommé (réservé à l'export RGPD annoncé).

**Suggestion** : le retirer, ou le livrer dans la MR du `CustomerPersonalDataProviderInterface`
(tag `thelia.customer.personal_data_provider`) qui le consommera.

### [Service/Api/ProductQuestionPayloadMapper.php:46-53] + [Service/Front/AnsweredQuestionsPresenter.php:57-60] `mixed` et deux normalisations de date

**Problème** : les getters Propel renvoient `string|\DateTimeInterface|null` ; les deux helpers
`date(mixed)` refont la même réduction. Idem `ProductQuestionListFilters::knownStatus/positiveInt/nonEmpty(mixed)`
face à `InputBag::get()`.

**Suggestion** : un `PropelDate::toImmutable(string|int|\DateTimeInterface|null): ?\DateTimeImmutable`
partagé ; typer les réducteurs de filtres sur l'union d'`InputBag`.

### [.github/workflows/release.yml:7] Workflow réutilisable sur `@main`

**Problème** : le contenu exécuté est celui du dépôt tiers au moment du push : chaîne
d'approvisionnement non figée.

**Suggestion** : épingler sur un SHA ou un tag, avec commentaire de version.

## 🟣 Pré-existant (hors module, ticket séparé)

### [core/lib/Thelia/Tools/TokenProvider.php:84] Jeton CSRF BO comparé avec `!==`, jamais roté

**Problème** : comparaison non constant-time et jeton unique par session ; le module s'appuie
dessus pour refuse/delete.

**Suggestion** : `hash_equals()` dans le core.

### [vendor/symfony/ux-live-component/…/LiveComponentSubscriber.php:359] CSRF des live actions = en-tête + SameSite

**Problème** : depuis UX 2.21 le paramètre `csrf` de `#[AsLiveComponent]` est sans effet ; la
protection repose sur `X-Requested-With` et le `SameSite` du cookie de session (non vérifié dans
la config du core). Le formulaire Thelia embarqué garde son propre `_token`, qui couvre `ask()`
indépendamment.

## ✅ Points positifs

- Les deux portes passent par `ProductQuestionAsker`, `ProductQuestionAnswerer`,
  `ProductQuestionRefuser` et le même sanitizer : aucune règle métier dupliquée entre front et API.
- API : `security` sur les trois opérations, POST sous le firewall `^/api/front/account` **et**
  `is_granted('ROLE_CUSTOMER')`, `validationContext` posé, client lu sur le token jamais dans le
  corps, guest rejeté par les deux implémentations de `CurrentCustomerInterface`, payload champ
  par champ sans `customerId`/`answeredBy`/statut, brouillon masqué hors publié, 404 identique
  pour absent/pending/refusé.
- Front live : les quatre `LiveProp` sont dans le checksum (`hash_equals`), `text|raw` du
  SnackBar ne reçoit que des chaînes serveur, formulaire Thelia avec son `_token`, `nl2br`
  pré-échappe.
- Back-office : `checkModuleAccess` sur les cinq actions au bon niveau, méthodes HTTP
  restreintes, `requirements` sur `{id}`, CSRF vérifié serveur sur les trois écritures, tri
  blanchi par `in_array` strict, `joinWith('Customer', LEFT_JOIN)` et `titlesFor()` en un seul
  `IN` : pas de N+1.
- Sanitizer : boucle jusqu'à stabilisation sur les entités doublement encodées, caractères
  invisibles et bidi retirés, `strip_tags` évité à raison.
- Schéma : `TheliaMain`, FK et `onDelete` conformes aux décisions gelées, index composite calqué
  sur la requête front ; `firstAnswer` lu avant le changement d'état ; listeners qui journalisent
  et ne propagent jamais.
- Aucun secret, aucun `.env`, aucun fichier de cache versionné.
